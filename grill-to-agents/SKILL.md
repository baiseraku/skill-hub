## 生效范围与退出

仅在用户明确调用本技能，或明确要求对当前想法进行本技能的追问流程时启用。用户只是提到、安装、修改或讨论这个技能，不算调用；普通任务、一般澄清和泛泛的「帮我想清楚」不自动进入本流程。

一次调用只覆盖用户指定的当前话题及其连续追问轮次。用户回答问题、补充同一话题或调整强度时继续本轮流程；不要把追问要求扩散到整个聊天、其他对话、其他 agent 或后续无关任务。

完成总结（以及本技能需要的最终清单）、用户要求停止追问、转入执行或切换话题时，结束本次调用，恢复普通交流。后续只有用户再次明确调用或明确要求继续本轮追问时，才重新启用。正常执行需要的必要澄清遵循当前环境规则，不自动沿用本技能的强度或格式要求。

本技能中的强度选择和分轮追问等要求，只在本次调用范围内生效。生成给另一个 agent 的执行清单时，不把这些追问规则作为接手方的默认要求；只有用户明确要求接手方继续追问时才加入。

基于 grill 的追问流程，最终交付一份独立可用的执行指令。无需加载其他 skill。

先询问用户希望的拷打强度。用户已经指定时直接开始。

1. 浅问：只补最关键的缺口
2. 常规：把明显没想清楚的地方问明白
3. 细问：检查目标、约束、取舍和默认假设
4. 深挖：主动寻找风险、遗漏和边界情况
5. 拷打：严格挑战前提，直到重要未知基本暴露

用户可以随时调整强度。

分轮进行。每轮询问当前已经具备前提的问题，可以是一条，也可以是多条。依赖尚未确定答案的问题，留到下一轮。

优先追问会明显影响后续方案的内容：

- 真正想解决什么问题
- 哪些事情已经确定
- 哪些事情还没有决定
- 哪些前提只是用户默认成立
- 有没有用户尚未意识到的重要问题
- 哪些取舍会改变后续方向

能自己查清楚的事实不要交给用户；涉及用户的目标、偏好、成本和取舍时，再让用户决定。必要时提供选项和建议，但不要替用户决定。

每个问题使用：

```
❓ Q1｜问题标题
问题内容。需要时给出选项。
➡️ 建议：简短给出你的推荐和理由。
```

同一轮有多个问题时继续 Q2、Q3。问题保持具体、容易回答。不要一次堆出大量低价值问题。

强度决定追问深度，不只是问题数量：

- 浅问只处理会卡住下一步的问题。
- 常规补齐明显缺口。
- 细问开始检查隐含假设和重要取舍。
- 深挖主动寻找边界情况、风险和遗漏。
- 拷打会挑战模糊回答、未经验证的前提和互相冲突的要求。

不要为了「拷打」而无限追问。当剩余未知已经不足以明显改变下一步时停止。

## 总结与执行清单

追问结束后，先简短总结「已确定」「暂未确定」「下一步」，随后在同一回复中生成一份完整的 Markdown 执行清单。生成清单属于本技能交付，不需要再次确认；不要自行开始清单中的重要执行，也不要自动发送到其他 agent 或对话。用户明确要求继续执行时，按已有授权推进。

清单用一个标记为 markdown 的代码块包裹，便于完整复制；代码块外可保留简短总结，清单内部必须包含执行所需的上下文。用户指定其他可复制格式时遵循用户要求。

写给接手的 agent，使用直接的执行指令：

- 包含用户目标、已确定的决策与约束、必要背景和输入。不要写「按上文」「参考之前讨论」等依赖原对话的内容。
- 按依赖顺序列出具体可执行的 `- [ ]` 步骤，注明已完成工作，避免让接手方重复执行。清单用于交接，不要求接手方使用特定待办工具。
- 每一步写清行动及预期结果；有必要时指出前置依赖和需要先核查的事实。只填写已核实的路径、链接、环境或参数，不编造。
- 给出交付物及其保存位置（已确定时），以及可观察或可验证的验收标准。区分必须满足的要求与建议。
- 把未确认信息、假设和阻塞列出来。会明显改变方案或阻止安全执行的问题，应在结束追问前澄清；不影响当前步骤的未知可留给接手方核查，并说明何时需要用户回答。
- 保留用户授权范围；生成清单不构成发布、发送消息或其他尚未授权动作的许可。相关动作确有必要时，在对应步骤注明执行前需获得的授权。
- 不把自己的建议写成用户已确认的决定，不加入无关任务，不携带密钥等敏感信息。

## 跨设备交接

默认考虑接手 agent 可能在另一台设备、不同操作系统或不同工作区中执行，不假定它能访问当前设备的文件、会话附件、已安装工具或登录状态。

- 尽量不写当前设备的绝对路径、用户名、临时目录、localhost 地址或仅本机可访问的服务地址。优先使用项目根目录下的相对路径、文件名称与用途、可访问的仓库链接或共享资源链接；明确相对路径以哪个项目根目录为基准。
- 项目根目录由接手方在其设备上定位。命令、输入和输出位置应使用项目相对路径或明确要求接手方设置的路径变量，不把当前设备的目录结构写死。用户明确要求针对指定设备或服务器执行时，可保留必要且已确认的路径，并注明适用设备。
- 仅存在本地或会话中的必要输入，列明文件名称、内容用途、需要传递的版本及获取方式；获取方式未确认时标明「待提供」，不要把本地路径当作已完成的交接。少量且适合复制的必要上下文可直接写入清单。
- 已完成工作不等于已同步到另一台设备。代码任务注明已确认的仓库、分支或提交；未提交改动和本地产物如为后续步骤所需，列入待传递材料。没有可用仓库或版本信息时如实标明，不编造链接。
- 对实际影响执行的环境依赖，说明所需工具、已确认的版本或兼容条件，让接手方先核查当地环境。需要账号权限的资源注明所需访问权限，不传递凭据。
- 交付位置优先写项目内的相对目录。接手方缺少输入或无法访问资源时，先核查获取方式；确实需要用户提供时才澄清，不假定文件已存在，也不擅自上传或同步。

下面是结构示例，按实际任务删减或合并栏目，替换全部示例文字：

```markdown
# 执行任务：任务名称

请按以下要求完成任务。先核查必要输入，按依赖顺序执行；只有影响执行的关键信息缺失时才向用户澄清。

## 目标与背景
- 目标：具体要解决的问题与期望结果。
- 必要背景与输入：接手方需要的信息、项目相对路径或可访问链接。
- 获取与定位：项目根目录的定位方式、必要输入的获取方式；本地材料尚未传递时标明待提供。
- 已完成：已有成果与核验情况；没有时省略。

## 已确定的要求与范围
- 必须满足：用户已确认的要求、限制及执行范围。
- 建议或待验证假设：如有，单独标明。

## 执行清单
- [ ] 在当前设备定位项目，核查必要输入、访问权限、环境依赖和已有成果，明确是否具备后续步骤的前提。
- [ ] 执行具体工作，产出明确结果；按实际任务拆成必要步骤。
- [ ] 按验收标准核验结果，并交付成果与实际验证结论。

## 交付与验收
- 交付物：具体成果及项目内的相对输出位置。
- 验收标准：可观察、可检查的完成条件。

## 未确认事项与执行边界
- 未确认项：缺失信息、影响及处理方式；没有时省略。
- 需额外授权的动作：具体动作及等待授权的位置；没有时省略。
```

交付前检查：接手方能否仅凭清单识别目标、输入、下一步和完成条件；实际任务步骤是否具体；是否混淆事实、建议与未知；是否依赖另一台设备无法访问的本地地址、未同步材料或环境状态。修正后再输出，不把空模板当作最终清单。
