# 科研进度报告：项目总结 → `report/`

一句话规则：**每次出报告，都在项目根目录的 `report/` 里留下一份「当前状态的唯一正本」——一份 markdown 主报告，加上报告正文引用到的图与表。**

`report/` 是稳定接口：用户和其他 agent 只看这一个位置，不看散落在 `output/`、`02_Figure/` 里的旧产物。所以它必须随时能反映最新进度，也必须能独立看懂——**默认读者是没参与这个项目的人或 agent**，凡是接手所需的信息（数据在哪、脚本怎么跑、参数在哪改、卡在哪）都要写进去。

## 0. 红线：只写当前项目文件夹里的真实数据

报告的价值全在真实。**编造一个数字，比少写一段、写「未记录」严重得多**——读者是拿这份报告去做判断和决定的，假数据比没有数据更坏。宁可交一份短而字字有据的报告，也不要一份长而好看却掺假的报告。

**范围同样是硬线：这份报告只总结当前项目文件夹里的东西。** 当前项目文件夹 = 含说明文件 / 脚本 / 数据目录的那一层（当前目录在子目录时，向上找到的那一层）。报告里的每个数字、每张图、每条结论、每个 accession，都要能在这个文件夹里指出对应的文件路径。范围之外的内容一律不写，哪怕它看起来很相关、很可信：

- **同一课题的兄弟项目文件夹**（如 `260925-1` 旁边的 `260925-2`、别人交付的目录、上一轮实验目录）：基因相同、疾病相同、平台相同也不许混进来——那些数字不是本项目的结果。用户明确要求跨项目汇总时另说，那次要逐条标出各自的项目来源，本 skill 的默认交付始终是单项目
- **其他会话的上下文与自己的记忆**：之前聊过的结论、看过但没落盘的分析、在别的项目里算过的值，本项目没有文件支撑的都不算数
- **外部资料与模型常识**：文献结论、数据库注释、领域背景。项目内有记录的按「背景」写，并与实测结果分开；项目内没有就写「项目内未记录背景」，不凭常识补一段

下面这些都算编造，一次都不行：

- 把估计、印象、常识写成具体值（「大约 15%」「约 300 个细胞」→ 只能是查出来的确切数字，查不到就写「未记录」）
- 从上一版报告、对话上下文或自己的记忆里抄数字——**必须回原始结果文件重新读**，上一版本身可能就是错的
- 把没跑、跑失败、报错的分析写成已完成或有结果
- 把 README、笔记、文献里的说法当成本项目的实测结果——那是「背景」，要和「结果」分开写
- 把其他项目文件夹、其他会话或自己的记忆里的数据与结论写成本项目的结果（本项目没做就写「未做」，没记就写「未记录」，不拿别处的内容填空）
- 凭印象写 accession、PMID、文献条目、软件版本、参数值，不回头核对
- 把模板、示例或其他项目里的数字留在报告里（P 值、样本数这类看着很像真的数字尤其容易漏）
- 手绘、示意、用模拟数据生成的图冒充结果图；示意图必须显式标注「示意图，非实测」
- 照图名猜图注，写出图里其实没有的内容

具体怎么做：

- 每个进入结论的数字，都在句内或括号里给出处（`output/02_de_results.csv`、`scripts/09_annotate.R` 里的阈值、日志行）。给不出出处的，从结论里删掉，或改写成「未记录 / 未验证」
- 数据文件与脚本注释、README 冲突时，**以数据文件为准**，并在报告第 6 节（已知问题）记一条「某处记载不一致」。多个数据文件之间冲突时（结果文件 vs 原始数据），优先信能追溯到脚本产出的结果文件；量级对不上就把两个都写出来，别替读者挑一个。有产物却找不到生成它的脚本或记录（链条缺失）也算一类，记「无法追溯」，不要编一条来源把它接上
- 项目里没有背景材料时，明写「项目内未记录背景，本节待补」，不要凭常识补一段领域背景——那是编造，不是背景
- 数据本身形似示例或占位（样本极少、命名像占位符、accession 只有一处且无来源记录）时，照写现状并点明「来源无法核对」——既不跳过不写，也不当确证结果
- 写得粗比写得假好：不确定就给区间或「未达显著」，不要凑精度，有效位数不要超出测量精度
- 交付前抽查 3–5 个关键数字，回原始文件逐个核对（是回原始文件，不是回上一版报告），对不上就改
- 「客观原因」也要有依据：说数据拿不到，就给出你查过的出处（accession 页面、访问被拒的记录、缺失文件的路径）；说做不到，就指出那条报错或限制写在哪个文件里。拿客观限制当「没做」的借口，与编造同等性质
- 项目里确实没有的东西，写「未做 / 未记录 / 未运行 / 无法核对」（没有这项分析 = 未做；做了但参数或来源没记下来 = 未记录；有代码没结果 = 未运行；只有一处记载、无从交叉验证 = 无法核对）——这是合格答案，不是失败

## 1. 先扫项目，再动笔

**扫描范围就是当前项目文件夹及其子目录**（含它下面的 `report/`）：不向上级目录、兄弟项目目录或其他位置找材料。按这个顺序读，读到的算事实，没读到的不写：

1. 项目说明与笔记：根目录 `README.md`、`AGENTS.md` / `CLAUDE.md`、`*_Notes.md`、`Draft.md` 等
2. 分析脚本：`*.R` / `*.py` / `*.ipynb` / `*.sh` / `*.do` / Snakemake、Nextflow 流程文件——逐个读分节标题与输入输出注释，弄清每一步在做什么、参数是多少
3. 数据目录：`Rawdata/`、`01_RawData/`、`data/`——记 accession、来源文献、物种、分组与样本数
4. 结果目录：`output/`、`results/`、`02_Figure/`、`03_Notes/`——已有的图、表、日志、中间对象
5. 文件时间与 git 记录：判断「当前进度到哪一步」——哪些脚本已经跑出结果，哪些只是写了还没运行

清单是**查找范围**，不是必做项：项目里没有的跳过，别为一份不存在的 `Draft.md` 或 `CLAUDE.md` 反复翻目录——早期小项目扫完只要几分钟。同理，某个信息在本项目里找不到时，按第 0 节写「未记录 / 未做」，不要到项目文件夹之外（兄弟项目、过往会话、记忆、文献）去补——补来的东西不属于这份报告。

写的时候另外守两条格式要求（真实性的红线见上一节，冲突时红线优先）：

- **数据集给 accession**（GSE / PRJNA / E-MTAB / PMID），不给「某公共数据集」
- **参数给具体值**（阈值、dims、分辨率、软件及版本、参考基因组、基因集库、检验方法），不给「标准参数」

项目还很早期（只有零散文件、没有结果）时，如实写「处于起步阶段、已有什么、缺什么」，为凑结构编内容是这份报告最严重的失败。

## 3. 图与表

- **图是可选要素**：报告可以一张图都没有。没有能挂到具体结论上的图时，零图 + 在正文写明原因（结果还没产出、现有图与结论不相干），不要为了「有图」硬塞一张
- **图是证据，不是正文**：每张图要挂在一个具体结论下面，正文里说清它证明什么。装饰性的、纯展示流程的图不要放
- **证据规则优先于搬运规则**：结果目录里有图 ≠ 要搬进 `report/`。先看这张图证明什么，挂不上结论的不搬
- **打开看，别照文件名猜**：图名与图的实际内容不符时以内容为准（图注按内容写，或者干脆排除并在第 6 节记一条）。图名前缀只是命名约定，不代表图一定由同编号脚本产出
- **只放重要且必要的**：一个主要结论 1–2 张；同一个结果的多个视图先合并。全篇十几张以上时，先问哪些是重复的
- **默认不新造图**：报告搬运项目里已有的产物。若某个结论确实缺一张能说明问题的图、而手上的数据画得出来，可以画，但要满足三条——作图代码落盘到项目脚本（不要只存在于这次生成过程里）、图注注明由哪个脚本生成、数据从项目文件读。手绘或示意图一律按第 0 节标注「非实测」
- **格式**：PNG 和 PDF 都可以。已有的 PDF 图直接放进 `report/` 引用即可；需要 markdown 内联预览时用 `scripts/pdf2png.sh` 转成 PNG
- **优先让作图代码直接出图**（`ggsave(..., dpi = 300)`、`plt.savefig(dpi = 300)`、Prism 导出），比事后转换更保真。转换脚本只作回退
- **命名**：`<脚本号>_<内容>_p<页号>.png`，如 `09_sfrp2_by_disease_p1.png`——前缀是生成它的脚本编号，多页图按页拆开。图名用小写英文与下划线，不用中文与空格
- **从结果目录复制现成的 PNG 就保持原名**；由 PDF 转出来的按 `<pdf 基名>_p<页号>.png`（`pdf2png.sh` 就是这个命名）
- **表**：3–8 行的关键结果内联成 markdown 表（读者不用下载就能看）；长表（>20 行）导出 csv 放 `report/assets/`，正文说明它是什么、在哪
- **图注一句话**，说画的是什么、分组是什么；不要把结论复述一遍

## 4. 写入 `report/`

**定位项目根**：含说明文件、脚本或数据目录的那一层（当前目录在子目录时要向上找），`report/` 建在它下面，不要建在 `output/` 或某个分析子目录里。

**主报告文件名**用研究主题命名（ASCII，如 `SFRP2_ICI_colitis.md`、`scRNA_QC_progress.md`），**不要叫 `report.md`**——多个项目汇总时文件名要能表意。`report/` 里除了主报告还有**本 skill 生成/维护**的其他报告 md 时，加一份 `README.md` 作索引指向各报告（索引也属每次重建那一类）；用户手写的 md 不算，不因它而建索引。

**覆盖语义**（用户要求：一个项目只有一个 `report/`，永远是最新的一版）：

1. 列出现有 `report/` 里的文件，逐个判：**本 skill 生成的产物**（主报告 md、索引 README.md、图、assets）→ 归入重建；**其他一切**（用户手写的笔记、从别的项目搬来的文件、看不清来历的东西）→ 留在原地，报告里如实提一句它是什么
2. 判据是来源与内容，不是文件名：名字符合本 skill 命名规范、内容却属于别的项目的，归「留」不归「删」。拿不准就留下并在交付时点出来——留下的代价是多一个文件，删错的代价是丢了用户的东西
3. 归入重建的旧版**移入废纸篓**再重建：

   ```bash
   ~/.agents/skills/trash-instead-of-delete/scripts/trash.sh <绝对路径...>
   ```

   该脚本自带 `trash` → `gio trash` → Finder → `mv` 的回退链（不要假定机器上一定装了 `trash`）；绝不用 `rm -rf report/`。移完把落点转述给用户
4. 重建目录并写入新文件
5. 写完核对：正文引用的每个图都在；第 1 步判为**重建**的图里，没有被引用的（上一版残留或这一版噪声）移入废纸篓；判为「留」的文件一律不动

**图从哪来**：图在 `output/`、`02_Figure/` 等结果目录里时，复制进 `report/`（保持正文相对路径引用）；不要用绝对路径引用，报告文件夹要能整体拷走。需要转换时：

```bash
~/.agents/skills/research-report/scripts/pdf2png.sh ./report 02_Figure/260914-1-1.pdf
# 回退链 pdftoppm → magick → pymupdf → R pdftools → qlmanage(macOS，只出第 1 页)
# 本机只有 qlmanage：多页 PDF 会转不全并给出警告，需要时 brew install poppler 后重跑
```

## 5. 语言与语气

- 中文写正文；基因名、软件名、通路名、统计量保留领域内的英文原文
- 首次出现的缩写给全称，读者没参与项目
- 结论句给方向和量级（「5.13% vs 0.49%，P = 0.028」），不写「显著升高」这类没有数字的判断
- 不写「综上所述」「值得注意的是」「本研究具有重要意义」这类填充句

## 6. 交付前自查

- **真实性抽检做过**：挑 3–5 个关键数字回原始文件核对过；报告里没有说不出出处的数字
- **范围没越界**：正文里的数字、图、结论、accession 全都出自当前项目文件夹，抽查的几条都能指出路径；没有从兄弟项目、其他会话或自己的记忆里搬来的内容（兄弟项目里的同类结果尤其容易顺手带进来）
- 没有用「约 / 大概 / 估计」兜着的数字；没跑或跑失败的分析都标了「未运行」；背景说法（文献、README）与实测结果分开写；示意图已标注「非实测」
- `report/` 在项目根下；主报告文件名表意，不是 `report.md`
- 五个必需要素都在：**研究主要方向、研究问题、原始数据来源（带 accession）、关键方法与参数、当前进度**

- 正文引用的图全部存在（相对路径）；有图时没有未被引用的残留，零图时正文说明了原因；格式为 PNG 或 PDF

- 已知问题与后续方向各自成节，且后续方向能对上已知问题
